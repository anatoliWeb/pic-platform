# RS485 Driver

## Description

RS485 protocol layer built on top of UART.
Provides direction control (DE/RE), byte transfer, and framed data exchange.

## API

- `rs485_init()` — initialize direction control pin, start in RX mode
- `rs485_set_tx()` — switch to transmit mode
- `rs485_set_rx()` — switch to receive mode
- `rs485_send_byte()` — send one byte (direction must be TX)
- `rs485_read_byte()` — read one byte (direction must be RX)
- `rs485_send_frame()` — blocking framed send with CRC16 Modbus
- `rs485_receive_frame()` — blocking framed receive with CRC validation
- `rs485_finish_tx()` — wait for TX completion, settling delay, RX restore
- `rs485_crc8()` — Dallas CRC8 helper

## Custom TX flow

For custom protocols where the caller owns frame format, CRC, and commands:

```c
rs485_set_tx();

uart_write_byte(custom_byte_1);
uart_write_byte(custom_byte_2);
uart_write_byte(custom_byte_3);

if (rs485_finish_tx() == 0u)
{
    /* Timeout: application handles retry or error policy. */
}
```

`rs485_finish_tx()` returns:
- `1` — TRMT became 1 before timeout, settling delay executed, RX restored
- `0` — TX-complete timeout, settling delay skipped, RX still restored

After `rs485_finish_tx()` returns, the line never stays in TX. Repeated transmissions work after timeout.

The caller owns: frame format, CRC, commands, retry/error policy. The platform handles: direction control, TRMT polling, settling delay, RX restore.

Minimum supported baud: 9600. See baud rate table below.

## Blocking behavior

- `rs485_finish_tx()` encapsulates the complete TX completion sequence: polls `TXSTAbits.TRMT` with a deterministic time-based timeout (poll interval `RS485_TX_COMPLETE_POLL_US` = 100 us, total timeout `RS485_TX_COMPLETE_TIMEOUT_US` = 10000 us = 10 ms). On success: 50 us settling delay, RX restored, returns 1. On timeout: settling delay skipped, RX restored, returns 0. Uses `DRV_DELAY_US()` for compiler-independent timing.
- `rs485_send_frame()` reuses `rs485_finish_tx()` internally — no duplicate TRMT polling, settling delay, or RX restore logic.
- `rs485_receive_frame()` blocks with a timeout while waiting for each byte. If no data arrives within `RS485_TIMEOUT_TICKS` (200 ms), the function returns 0.
- Direction switching includes guard delays (`DRV_DELAY_US(50u)`) before the first byte (in `rs485_send_frame()` only) to allow the MAX487 transceiver to settle.

## RX restore

- `rs485_finish_tx()` always calls `rs485_set_rx()` before returning — line never stays in TX, regardless of success or timeout.
- `rs485_send_frame()` reuses `rs485_finish_tx()`, inheriting the same RX restore guarantee.
- `rs485_receive_frame()` calls `rs485_set_rx()` at the start to ensure the transceiver is in receive mode.
- On timeout or CRC error, the function returns 0 but does not change the direction pin; the caller should call `rs485_set_rx()` if needed before the next receive attempt.

## Final byte preservation

- **XC8 wrapper** (verified): `rs485_finish_tx()` delegates to the static `rs485_wait_tx_complete()` which accumulates elapsed time via `DRV_DELAY_US(100u)` per poll and compares against `RS485_TX_COMPLETE_TIMEOUT_US` (10000 us = 10 ms). On success, a 50 us settling delay allows MAX487 to settle before direction switching. RX is always restored. `rs485_send_frame()` reuses `rs485_finish_tx()` — no duplicate algorithm.
- **C18 wrapper** (not build-verified): identical implementation. `rs485_finish_tx()` with the same TRMT polling, settling delay, and RX restore. The C18 compiler provides SFR access automatically based on the target device. C18 toolchain was not available for build verification.
- **Shared fallback** (`#else` block): unreachable dead code. `core/compiler.h` requires `DRV_COMPILER_XC8` or `DRV_COMPILER_C18`, otherwise compilation fails with `#error`. Updated for consistency but never executed.

## Supported baud rates

**Minimum supported baud: 9600.** The TX-complete timeout of 10 ms is designed for 9600 baud and above. At 9600 baud one byte (10 bits) takes ~1.04 ms; the timeout provides ~10x margin.

| Baud rate | Byte time (10 bits) | Timeout margin | Status |
|---|---|---|---|
| 9600 | ~1.04 ms | ~10x | supported |
| 19200 | ~0.52 ms | ~20x | supported |
| 57600 | ~0.17 ms | ~60x | supported |
| 115200 | ~0.087 ms | ~115x | supported |

Baud rates below 9600 (e.g. 1200, 600) are **not supported** by the RS485 driver. The RS485 API does not accept a baud rate parameter — the caller must configure the UART via `uart_init()` before calling `rs485_init()`. The 10 ms timeout assumes the UART is configured for 9600 baud or higher. Using a lower baud rate may cause a false TX-complete timeout before the last stop bit finishes transmitting.

All tracked examples use `uart_init(9600u)`.

## Error recovery

- TX-complete timeout: `rs485_finish_tx()` returns 0, RX is restored. `rs485_send_frame()` propagates the same status. Repeated send after timeout works.
- `uart_write_byte()` has no error return (hardware limitation). The only detectable failure is TX-complete timeout.
- On receive timeout or CRC error, the function returns 0. The caller is responsible for retrying or switching direction.

## Example

### Platform frame send

```c
uint8_t tx_data[3] = {0x10u, 0x20u, 0x30u};
uint8_t rx_data[16];

rs485_init(&PORTB, &TRISB, 2u);
rs485_send_frame(tx_data, 3u);                     // blocking send
len = rs485_receive_frame(rx_data, sizeof(rx_data)); // blocking receive
```

### Custom protocol TX

```c
rs485_init(&PORTB, &TRISB, 2u);

rs485_set_tx();
uart_write_byte(custom_byte_1);
uart_write_byte(custom_byte_2);
uart_write_byte(custom_byte_3);

if (rs485_finish_tx() == 0u)
{
    /* Timeout: application handles retry or error policy. */
}
```

## Notes

- TX/RX direction is controlled by DE/RE pin via GPIO.
- Frame integrity is validated by internal CRC check (current API exposes `rs485_crc8`).
- The driver is single-instance (static globals for direction pin).
- No non-blocking API is provided; the blocking model is intentional for simple half-duplex protocols.
