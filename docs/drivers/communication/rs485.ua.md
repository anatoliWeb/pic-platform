# RS485 Драйвер

## Опис

RS485 протокольний шар поверх UART.
Надає керування напрямком (DE/RE), побайтовий обмін і обмін кадрами.

## API

- `rs485_init()` — ініціалізація піна напрямку, старт у режимі RX
- `rs485_set_tx()` — переключення в режим передачі
- `rs485_set_rx()` — переключення в режим прийому
- `rs485_send_byte()` — відправка одного байту (напрямок має бути TX)
- `rs485_read_byte()` — зчитування одного байту (напрямок має бути RX)
- `rs485_send_frame()` — блокуюча відправка кадру з CRC16 Modbus
- `rs485_receive_frame()` — блокуючий прийом кадру з валідацією CRC
- `rs485_crc8()` — хелпер Dallas CRC8

## Блокуюча поведінка

- `rs485_send_frame()` блокується до повного висилання всіх байтів через UART. Опитує `TXSTAbits.TRMT` з часовим таймаутом 10 мс (100 ітерацій x 100 us через `DRV_DELAY_US`). Функція повертається щойно TRMT стане 1 — 10 мс є верхньою межею, а не фіксованою затримкою. При 9600 baud один байт передається ~1.04 мс; таймаут забезпечує 10-кратний запас. При таймауті функція повертає 0 і відновлює RX режим. При успіху повертає 1 після затримки стабілізації 50 us.
- `rs485_receive_frame()` блокується з таймаутом при очікуванні кожного байту. Якщо дані не надходять протягом `RS485_TIMEOUT_TICKS` (200 мс), функція повертає 0.
- Переключення напрямку включає захисні затримки (`DRV_DELAY_US(50u)`) перед першим байтом і після останнього біту (затримка стабілізації, а не гарантія останнього байту) для стабілізації трансивера MAX487.

## Відновлення RX

- `rs485_send_frame()` завжди викликає `rs485_set_rx()` перед поверненням — лінія ніколи не лишається в TX після повернення з публічного API, незалежно від успіху чи таймауту.
- `rs485_receive_frame()` викликає `rs485_set_rx()` на початку для гарантування режиму прийому.
- При таймауті або помилці CRC функція повертає 0, але не змінює пін напрямку; викликаючий має викликати `rs485_set_rx()` при потребі перед наступним прийомом.

## Збереження останнього байту

- **XC8 обгортка** (підтверджено): `rs485_wait_tx_complete()` опитує `TXSTAbits.TRMT` з часовим таймаутом через `DRV_DELAY_US(100u)` за ітерацію, максимум 100 ітерацій (10 мс загалом). Використовує ту саму інфраструктуру затримок, що й таймаут `rs485_receive_frame()`, забезпечуючи детерміновану поведінку незалежно від оптимізації компілятора. При успіху захисна затримка 50 us дозволяє трансиверу MAX487 стабілізуватися перед переключенням напрямку. При таймауті функція повертає 0, RX все одно відновлюється.
- **C18 обгортка** (build не підтверджено): ідентичне часове опитування TRMT. Компілятор C18 забезпечує доступ до SFR автоматично на основі цільового пристрою. Компілятор C18 був недоступний для перевірки збірки.
- **Спільний fallback** (`#else` блок): мертвий код, який не може бути виконаний. `core/compiler.h` вимагає `DRV_COMPILER_XC8` або `DRV_COMPILER_C18`, інакше компіляція завершується помилкою `#error`. Оновлено для узгодженості, але ніколи не виконується.

## Підтримувані baud rates

Таймаут TX-complete 10 мс покриває всі стандартні UART baud rates:

| Baud rate | Час байту (10 бітів) | Запас таймауту |
|---|---|---|
| 9600 | ~1.04 мс | ~10x |
| 19200 | ~0.52 мс | ~20x |
| 57600 | ~0.17 мс | ~60x |
| 115200 | ~0.087 мс | ~115x |

## Відновлення помилок

- Таймаут TX-complete: `rs485_send_frame()` повертає 0, RX відновлюється. Повторна відправка після таймауту працює.
- `uart_write_byte()` не має звіту про помилку (апаратне обмеження). Єдина виявляема помилка — таймаут TX-complete.
- При таймауті прийому або помилці CRC функція повертає 0. Викликаючий відповідає за повторну спробу або переключення напрямку.

## Приклад

```c
uint8_t tx_data[3] = {0x10u, 0x20u, 0x30u};
uint8_t rx_data[16];

rs485_init(&PORTB, &TRISB, 2u);
rs485_send_frame(tx_data, 3u);                        // блокуюча відправка
len = rs485_receive_frame(rx_data, sizeof(rx_data)); // блокуючий прийом
```

## Особливості

- Керування TX/RX виконується через DE/RE пін із використанням GPIO.
- Цілісність кадру перевіряється внутрішнім CRC (у поточному API доступний `rs485_crc8`).
- Драйвер одинарний (статичні глобальні для піна напрямку).
- Неблокуючий API не надається; блокуюча модель навмисна для простих half-duplex протоколів.
