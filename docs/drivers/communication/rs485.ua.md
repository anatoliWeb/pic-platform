# RS485 Драйвер

## Опис

RS485 протокольний шар поверх UART.
Надає керування напрямком (DE/RE), побайтовий обмін і обмін кадрами.

## API

- `rs485_init()` — ініціалізація піна напрямку, старт у режимі RX
- `rs485_set_tx()` — переключення в режим передачі
- `rs485_set_rx()` — переключення в режим прийому
- `rs485_send_byte()` — відправка одного байту (напрямок має бути TX)
- `rs485_read_byte()` — зчитування одного байту (напрямок має бути RX)
- `rs485_send_frame()` — блокуюча відправка кадру з CRC16 Modbus
- `rs485_receive_frame()` — блокуючий прийом кадру з валідацією CRC
- `rs485_finish_tx()` — очікування завершення TX, затримка стабілізації, відновлення RX
- `rs485_crc8()` — хелпер Dallas CRC8

## Потік користувацької передачі

Для користувацьких протоколів, де викликаючий володіє форматом кадру, CRC та командами:

```c
rs485_set_tx();

uart_write_byte(custom_byte_1);
uart_write_byte(custom_byte_2);
uart_write_byte(custom_byte_3);

if (rs485_finish_tx() == 0u)
{
    /* Таймаут: додаток обробляє повторну спробу або політику помилок. */
}
```

`rs485_finish_tx()` повертає:
- `1` — TRMT став 1 до таймауту, затримка стабілізації виконана, RX відновлено
- `0` — таймаут TX-complete, затримка стабілізації пропущена, RX все одно відновлено

Після повернення з `rs485_finish_tx()` лінія ніколи не лишається в TX. Повторні передачі працюють після таймауту.

Викликаючий володіє: форматом кадру, CRC, командами, політикою повтору/помилок. Платформа обробляє: керування напрямком, опитування TRMT, затримку стабілізації, відновлення RX.

Мінімальний підтримуваний baud: 9600. Див. таблицю baud rates нижче.

## Блокуюча поведінка

- `rs485_finish_tx()` інкапсулює повну послідовність завершення TX: опитує `TXSTAbits.TRMT` з детермінованим часовим таймаутом (інтервал опитування `RS485_TX_COMPLETE_POLL_US` = 100 us, загальний таймаут `RS485_TX_COMPLETE_TIMEOUT_US` = 10000 us = 10 мс). При успіху: затримка стабілізації 50 us, RX відновлюється, повертає 1. При таймауті: затримка стабілізації пропущена, RX відновлюється, повертає 0. Використовує `DRV_DELAY_US()` для поведінки, незалежної від компілятора.
- `rs485_send_frame()` перевикористовує `rs485_finish_tx()` всередині — без дублювання TRMT polling, затримки стабілізації або відновлення RX.
- `rs485_receive_frame()` блокується з таймаутом при очікуванні кожного байту. Якщо дані не надходять протягом `RS485_TIMEOUT_TICKS` (200 мс), функція повертає 0.
- Переключення напрямку включає захисні затримки (`DRV_DELAY_US(50u)`) перед першим байтом (лише в `rs485_send_frame()`) для стабілізації трансивера MAX487.

## Відновлення RX

- `rs485_finish_tx()` завжди викликає `rs485_set_rx()` перед поверненням — лінія ніколи не лишається в TX, незалежно від успіху чи таймауту.
- `rs485_send_frame()` перевикористовує `rs485_finish_tx()`, успадковуючи ту саму гарантію відновлення RX.
- `rs485_receive_frame()` викликає `rs485_set_rx()` на початку для гарантування режиму прийому.
- При таймауті або помилці CRC функція повертає 0, але не змінює пін напрямку; викликаючий має викликати `rs485_set_rx()` при потребі перед наступним прийомом.

## Збереження останнього байту

- **XC8 обгортка** (підтверджено): `rs485_finish_tx()` делегує статичному `rs485_wait_tx_complete()`, який накопичує час через `DRV_DELAY_US(100u)` за опитуванням і порівнює з `RS485_TX_COMPLETE_TIMEOUT_US` (10000 us = 10 мс). При успіху захисна затримка 50 us дозволяє MAX487 стабілізуватися перед переключенням напрямку. RX завжди відновлюється. `rs485_send_frame()` перевикористовує `rs485_finish_tx()` — без дублювання алгоритму.
- **C18 обгортка** (build не підтверджено): ідентична реалізація. `rs485_finish_tx()` з тим самим TRMT polling, затримкою стабілізації та відновленням RX. Компілятор C18 забезпечує доступ до SFR автоматично на основі цільового пристрою. Компілятор C18 був недоступний для перевірки збірки.
- **Спільний fallback** (`#else` блок): мертвий код, який не може бути виконаний. `core/compiler.h` вимагає `DRV_COMPILER_XC8` або `DRV_COMPILER_C18`, інакше компіляція завершується помилкою `#error`. Оновлено для узгодженості, але ніколи не виконується.

## Підтримувані baud rates

**Мінімальний підтримуваний baud: 9600.** Таймаут TX-complete 10 мс розрахований для 9600 baud і вище. При 9600 baud один байт (10 бітів) передається ~1.04 мс; таймаут забезпечує ~10-кратний запас.

| Baud rate | Час байту (10 бітів) | Запас таймауту | Статус |
|---|---|---|---|
| 9600 | ~1.04 мс | ~10x | підтримується |
| 19200 | ~0.52 мс | ~20x | підтримується |
| 57600 | ~0.17 мс | ~60x | підтримується |
| 115200 | ~0.087 мс | ~115x | підтримується |

Baud rates нижче 9600 (наприклад, 1200, 600) **не підтримуються** драйвером RS485. API RS485 не приймає параметр baud rate — викликаючий має налаштувати UART через `uart_init()` перед викликом `rs485_init()`. Таймаут 10 мс припускає, що UART налаштовано на 9600 baud або вище. Використання нижчої швидкості може призвести до хибного таймауту TX-complete до завершення передачі останнього стоп-біту.

Всі відстежувані приклади використовують `uart_init(9600u)`.

## Відновлення помилок

- Таймаут TX-complete: `rs485_finish_tx()` повертає 0, RX відновлюється. `rs485_send_frame()` передає той самий статус. Повторна відправка після таймауту працює.
- `uart_write_byte()` не має звіту про помилку (апаратне обмеження). Єдина виявляема помилка — таймаут TX-complete.
- При таймауті прийому або помилці CRC функція повертає 0. Викликаючий відповідає за повторну спробу або переключення напрямку.

## Приклад

### Платформена відправка кадру

```c
uint8_t tx_data[3] = {0x10u, 0x20u, 0x30u};
uint8_t rx_data[16];

rs485_init(&PORTB, &TRISB, 2u);
rs485_send_frame(tx_data, 3u);                        // блокуюча відправка
len = rs485_receive_frame(rx_data, sizeof(rx_data)); // блокуючий прийом
```

### Користувацький протокол передачі

```c
rs485_init(&PORTB, &TRISB, 2u);

rs485_set_tx();
uart_write_byte(custom_byte_1);
uart_write_byte(custom_byte_2);
uart_write_byte(custom_byte_3);

if (rs485_finish_tx() == 0u)
{
    /* Таймаут: додаток обробляє повторну спробу або політику помилок. */
}
```

## Особливості

- Керування TX/RX виконується через DE/RE пін із використанням GPIO.
- Цілісність кадру перевіряється внутрішнім CRC (у поточному API доступний `rs485_crc8`).
- Драйвер одинарний (статичні глобальні для піна напрямку).
- Неблокуючий API не надається; блокуюча модель навмисна для простих half-duplex протоколів.
